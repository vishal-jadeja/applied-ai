Part 0

The foundation you already have

Ten leaps, each one fixing the wall the previous idea hit. Everything below builds on these — when a new concept lands, it will point back to the leap it extends.

Five ideas from the journey carry everything on this page. If any feels shaky, revisit that lesson before continuing:

Lesson 4 · 6
The training loop

Guess → measure error (loss) → nudge every knob downhill (gradient descent via backprop) → repeat. Every model below learns exactly this way.

Lesson 8
Meaning is geometry

A word (soon: a token, an image, a document) becomes a dense vector positioned so that similar things sit close together.

Lesson 10
Attention

Every token asks every other token “are you relevant to me?” (Q·K), then rebuilds itself as a weighted blend of their content (V). Parallel, no distance limit.

Lesson 11
Next-token prediction

An LLM is a big Transformer trained only to guess the next token. Text is its own answer key, so the whole internet is training data.

Lesson 12
The agent loop

Intelligence from the model, agency from the loop: the LLM emits a text request for an action, a harness runs it, the result is pasted back in.

Part A · The life of a prompt

Inside the model

Follow one request through a modern LLM, in order: text becomes tokens (A1), tokens get positions (A3), they flow through Transformer blocks (A4) — often sparse ones (A5) — out comes a probability distribution to sample from (A2), and a cache makes generating fast (A6).

A1step 1 · before embeddings

Tokenization — how text becomes numbers

The wall

Lesson 8 jumped from words to embeddings, but a model can’t look words up: a fixed word list either misses “unbelievable”, typos, code, and Hindi — or explodes to millions of entries. Going letter-by-letter fits everything but makes every sequence painfully long. Neither works.

The idea

Split text into tokens — reusable chunks that are usually parts of words. Byte-Pair Encoding (BPE) learns the chunks from data: start with raw bytes (so nothing is ever “unknown”), count which adjacent pair appears most often in a huge text corpus, merge that pair into a new token, and repeat ~50,000–100,000 times. Common words end up as one token; rare words get built from familiar pieces. Each token gets an ID number, and that ID is what looks up the embedding vector from Lesson 8.

Why it matters

  • Token limits and pricing are counted in these chunks — that’s what “200k context” and “$ per million tokens” actually measure.
  • Models miscount letters (the “strawberry” problem) because they never see letters — “strawberry” may arrive as 2–3 opaque chunks.
  • Non-English costs more: BPE merges were learned mostly on English, so Hindi or code with unusual identifiers fragments into more tokens for the same meaning.
A3step 2 · giving tokens a place

RoPE — modern positions & long context

The wall

Lesson 10 said attention is order-blind, so 2017’s Transformer added a fixed wave-pattern “position stamp” to each vector (sinusoidal encoding). It works, but it encodes “I am token #4021” — an absolute address. For language, what matters is “this word is 2 tokens before that one” — a relative distance. Absolute stamps also generalize badly past the lengths seen in training.

The idea

RoPE (Rotary Position Embedding): instead of adding a stamp, rotate each token’s Query and Key vectors by an angle proportional to its position (position 5 → rotate 5θ). The attention score is a dot product, and a dot product between two rotated vectors depends only on the angle between them — which is the relative distance. Position becomes rotation, and distance becomes an angle.

Why it matters

  • Nearly every modern open model (Llama, Mistral, Qwen, DeepSeek) uses RoPE — “sinusoidal” survives only in the 2017 paper.
  • Long context (100k–1M tokens) is largely achieved by stretching RoPE’s rotation frequencies (interpolation / YaRN-style scaling) plus training on long documents.
  • What still breaks at length: attention gets diluted over more tokens, and models attend best to the start and end of the window — the lost-in-the-middle effect. Where you place things in a long prompt genuinely matters.
A4step 3 · the repeating unit

The Transformer block, fully

The wall

Lesson 10 gave you attention — but attention alone, stacked 80 layers deep, would not train. The gradient signal would shrink layer by layer (the vanishing-gradient problem from Lesson 7, back again), and there would be nowhere for per-token computation and stored knowledge to live. The real block has three more parts, each load-bearing.

The idea

One block = attention plus a small feed-forward network, with two tricks wrapped around both:

  • Residual connection — instead of replacing the token’s vector, each sublayer adds its result to the incoming vector (x + f(x)). This creates a “highway” the gradient can flow straight down during backprop — no shrinking — which is what lets Transformers go 100+ layers deep.
  • Layer normalization — before each sublayer, rescale the vector to a standard size so numbers never drift toward exploding or vanishing as depth grows.
  • MLP / feed-forward sublayer — a plain two-layer network (expand ~4×, activate, project back) applied to each token separately. Attention moves information between tokens; the MLP transforms it within a token. This is where most learned facts are stored — roughly two-thirds of all parameters.

Why it matters

  • This closes the loop with Lesson 7: residuals + normalization are the reason vanishing gradients don’t kill 100-layer models.
  • You can’t build a GPT from scratch (your Phase-3 goal) without these — attention is maybe 30 lines; the block structure is the rest.
  • Knowing “facts live mostly in the MLPs, routing lives in attention” is the mental model behind interpretability, fine-tuning, and MoE (next).
A5step 4 · scaling the block

Mixture-of-Experts — big brain, small bill

The wall

Scaling laws (Lesson 11) say more parameters = smarter. But in a dense model, every token’s forward pass multiplies through every parameter — so 10× the brain is 10× the compute for each of the trillions of tokens processed. Cost grows exactly as fast as capability.

The idea

Replace the block’s single MLP with many parallel experts (identical MLPs with different learned weights) plus a tiny router — a learned layer that scores which experts fit the current token and sends it to only the top 1–2. The blend of their outputs continues down the network. Result: enormous total parameters (capacity), small active parameters (cost per token). Specialization is learned, not assigned — nobody labels an expert “the code one.”

Why it matters

  • This is how frontier models (GPT-4-class, DeepSeek-V3, Mixtral, Llama 4) scale capacity without scaling per-token price — MoE is now the default at the top end, not the exception.
  • Explains spec sheets like “671B parameters, 37B active” (DeepSeek-V3) — total vs active is exactly the dense/sparse distinction.
  • The trade: all experts must sit in GPU memory even though few run — MoE buys compute efficiency by spending memory.
A2step 5 · the output end

Sampling & decoding — picking the next token

The wall

“Predict the next token” (Lesson 11) actually ends with the model producing logits — one raw score per vocabulary entry — turned by softmax into a probability for every possible next token. That’s a distribution, not a choice. Always taking the single most likely token (greedy decoding) sounds right but produces repetitive, bland text and loops (“the best of the best of the best…”).

The idea

Sample from the distribution, with knobs that reshape it first:

  • Temperature divides the logits before softmax. Low T (<1) sharpens the distribution toward the favorite (predictable, good for code and extraction); high T (>1) flattens it (varied, good for brainstorming); T→0 is greedy.
  • Top-k keeps only the k highest-probability tokens, then samples among them.
  • Top-p / nucleus keeps the smallest set whose probabilities sum to p (say 0.9) — the cutoff adapts: tight when the model is confident, wide when it’s unsure.
  • Beam search tracks several candidate continuations and keeps the best-scoring whole sequence — used in translation, rarely in chat (too bland).

Why it matters

  • These are the exact API knobs you already ship with — now you know what they do before softmax, not by folklore.
  • Practical defaults: extraction / classification / code → T ≈ 0–0.3; drafting and ideation → T ≈ 0.7–1.0. Don’t crank temperature and top-p at once; you’re stacking two tail-widening knobs.
  • “Non-determinism” of LLMs lives here: T = 0 makes output near-deterministic — the model itself was never random, the picker is.
A6step 6 · serving it fast

KV cache — why generation doesn’t re-read everything

The wall

Attention makes token N look at all N−1 tokens before it. Generating token 1001 therefore needs the Keys and Values of tokens 1–1000 — and naively you’d recompute all of them for every new token. Generation cost would explode quadratically, and long chats would crawl.

The idea

A token’s K and V never change once computed — so compute them once and keep them in GPU memory: the KV cache. Serving then has two phases with very different shapes: prefill — the whole prompt is processed in one parallel pass (the Transformer’s superpower from Lesson 10), filling the cache; then decode — one token per step, each new token computing only its own Q/K/V, reading everyone else’s from the cache, and appending its own column.

Why it matters

  • Explains the pricing you already pay: input tokens are cheap (parallel prefill), output tokens cost more (sequential decode), and prompt caching is literally “we kept the KV cache of your prompt prefix — reuse it for pennies.”
  • Explains time-to-first-token vs tokens-per-second — the two latency numbers that matter when you ship chat UIs.
  • Put the stable part of your prompt (system message, docs) first and the changing part last — caches match prefixes.
Part B · From autocomplete to assistant

Training & alignment, the modern way

Lesson 11 ended at SFT + RLHF (2022). The field kept moving: preferences without a reward model (B1), models that think longer instead of growing bigger (B2), tuning and running giants cheaply (B3), and steering with words alone (B4).

B1alignment · 2023→

DPO & RLVR — beyond RLHF

The wall

RLHF works but is heavy machinery: collect human rankings → train a separate reward model to imitate the rankings → run reinforcement learning (PPO) against it, juggling three or four model copies at once, unstable and easy to reward-hack (the model finds outputs the reward model over-scores — flattery, padding — rather than genuinely better answers).

The idea

Two simplifications, for two different goals:

  • DPO (Direct Preference Optimization) — a bit of math shows the RLHF objective can be rewritten as a plain loss on preference pairs: given (prompt, chosen answer, rejected answer), directly raise the model’s probability of the chosen one and lower the rejected one. No reward model, no RL loop — just ordinary fine-tuning on comparisons.
  • RLVR (RL from Verifiable Rewards) — for domains where correctness is checkable (does the code pass tests? does the math answer match?), drop human opinion entirely: generate attempts, check them with a verifier (a program, not a model), reward the correct ones. Rewards can’t be sweet-talked — you can’t flatter a unit test.

Why it matters

  • DPO is how most open-weight models you can download (Llama, Zephyr lineage, many fine-tunes) actually got aligned — it’s cheap enough for a single team.
  • RLVR is the bridge to reasoning models (next section): verifiable rewards are what trained the long “thinking” behavior of o1/R1-class models.
  • Interview-ready one-liner: RLHF learns a judge and plays against it; DPO learns from verdicts directly; RLVR replaces the judge with a test suite.
B2the 2025–26 frontier

Reasoning models — spending compute at answer time

The wall

Scaling laws scale training: more parameters, more data, more GPUs — and each step up costs exponentially more for smoother-but-shrinking gains. Meanwhile a giant model still answers a hard math problem with the same single forward pass as an easy one. Humans don’t work like that — hard problems get more time, not a bigger brain.

The idea

Test-time compute: let the model generate a long private chain of reasoning — trying approaches, checking itself, backtracking — before committing to an answer. This isn’t prompted (that’s B4); it’s trained in with RLVR: sample many long attempts at verifiable problems, reward the chains that end correct. The model learns that exploring and self-checking gets rewarded. Result: answer quality now scales with a second axis — thinking tokens — that you buy per-question instead of per-model.

Why it matters

  • Why a medium “thinking” model beats a huge instant one on hard tasks — the field’s scaling strategy shifted from train-time to test-time in 2024–25.
  • As a builder you now choose a thinking budget per request: pay latency and tokens for hard queries, skip it for easy ones. Routing between the two is a real product skill.
  • DeepSeek-R1 showed the recipe openly: base model + RLVR on math/code → reasoning emerges, no secret ingredient.
B3efficiency for builders

LoRA & quantization — big models on small budgets

The wall

Full fine-tuning updates every weight: for a 70B model that means cluster-scale GPUs, and a full 140 GB copy of the model per customization. Even just running it needs that memory. Adapting or self-hosting frontier-class models looks reserved for labs.

The idea

Two independent tricks, often combined (QLoRA):

  • LoRA (Low-Rank Adaptation) — freeze the pretrained weights. Next to each big weight matrix W, add a bypass of two thin matrices A and B (rank r ≈ 8–64) and train only those — typically <1% of parameters. The update a fine-tune needs is mostly low-rank, so the thin bypass captures it. Ship the adapter (megabytes), swap adapters per task on one base model.
  • Quantization — store weights in fewer bits. Training used 16-bit floats; for inference, 8-bit or 4-bit integers lose little quality because you keep per-group scale factors. Half to quarter the memory, faster loads.

Why it matters

  • This is the entire local-AI ecosystem you’ve seen: Ollama and GGUF files are quantized weights; the “fine-tunes” on Hugging Face are mostly LoRA adapters.
  • Product pattern: one hosted base model + a hot-swappable adapter per tenant/task, instead of N full copies.
  • Grounding: LoRA works because a fine-tune barely moves the weights — the knowledge was already there (pretraining, Lesson 11); tuning mostly reshapes behavior.
B4the cheapest lever

Prompting & chain-of-thought, from the inside

The wall

You usually can’t touch the weights at all — the model is behind an API. Yet behavior clearly changes with wording. Lesson 11 named the phenomenon (in-context learning: learning a task from examples in the prompt, no weight updates) but not the mechanism. Why does “think step by step” — just words — make a model better at math?

The idea

A prompt doesn’t teach; it conditions. The model computes p(next token | everything so far), so everything you write selects which region of its training distribution it continues from. Three levers, in order of power:

  • Few-shot examples — show 2–5 input→output pairs and the model locks onto the pattern and format. Attention heads literally copy the demonstrated structure forward; examples beat descriptions.
  • Chain-of-thought (CoT) — ask for reasoning before the answer. Mechanically: each generated token gets a full pass through the network, so a 200-token reasoning chain is 200× more forward passes than a one-token answer — CoT buys the model compute and working memory (its own intermediate results become input it can read). B2’s reasoning models are this, trained-in.
  • Role / format constraints — system prompts, output schemas (“reply as JSON matching…”), and delimiters shrink the space of plausible continuations, which is most of what “prompt engineering” in production is.
Extract the deal terms. Think step by step first, then output JSON.

Example:
Text: "Acme leases 2 floors at $40/sqft for 5 years starting Jan 2027."
Reasoning: lessee = Acme; rate = $40/sqft; term = 5 years; start = 2027-01.
JSON: {"lessee":"Acme","rate_sqft":40,"term_years":5,"start":"2027-01"}

Text: "BetaCorp signs a 3-year sublease at $55/sqft from March 2026."
Reasoning:

One prompt, all three levers: an instruction, a worked example (few-shot), reasoning before output (CoT), and a fixed schema — ending mid-pattern so the model must continue it.

Why it matters

  • Prompting is the cheapest lever you own — iterate in minutes, deploy with a string change; always exhaust it before reaching for fine-tuning.
  • Knowing the mechanism predicts behavior: CoT helps multi-step problems (more compute helps) but not fact lookup (the fact is either stored or it isn’t).
  • Prompts are code: version them, write eval cases for them (C1), and review changes like any other diff.
Part C · Around the model

Systems you build — RAG, agents, MCP, evals

The model is a component. Applied AI work — your work — is mostly the system around it: feeding it the right knowledge (C2), letting it act (C2), standardizing its tools (C3), and proving any of it works (C1).

C2grounding · you’ve shipped this — now own the internals

RAG — retrieval-augmented generation, from first principles

The wall

The model’s knowledge froze at training time, it has never seen your private data, the context window can’t hold your whole knowledge base — and when it doesn’t know, it hallucinates: generates fluent, confident text that is simply the most plausible continuation, not a retrieved fact. (It was trained to predict text, never to say “I don’t know.”)

The idea

Don’t put knowledge in the model; hand it the right page at question time. Two lanes:

  • Ingest (offline, once): split documents into chunks (a few hundred tokens each, ideally along natural boundaries); run each through an embedding model (Lesson 8 scaled up: whole passages → one meaning-vector); store vectors + text in a vector database, which is an index built for “find the nearest vectors fast.”
  • Query (online, every request): embed the question with the same model, fetch the top-k nearest chunks (nearest = most similar meaning, usually by cosine similarity — the angle between vectors), optionally rerank them with a more careful model, then build a prompt: “Answer using only these excerpts, cite them” + chunks + question.

Why it matters

  • RAG is the workhorse of applied AI — cheaper than fine-tuning, updates instantly (re-ingest a doc), and citations make answers auditable.
  • Debugging RAG = knowing which lane failed: if the right chunk wasn’t retrieved, no prompt will save you; if it was retrieved and ignored, no retriever will. Measure retrieval and generation separately (C1).
  • Your Phase-2 gate is to build this with no framework — embedding call, cosine similarity in a loop, prompt assembly — and your 02a-rag-basics notes already start there. The whole pipeline is ~100 lines.
C2action · lesson 12, now with engineering detail

Agents — the ReAct loop as a system you operate

The wall

Lesson 12 gave the concept: Thought → Action → Observation. Building one surfaces what the concept hides — the loop is a distributed system with an unreliable component in the middle. Errors compound (95% per-step reliability ≈ 60% over 10 steps), the context fills with tool output, and the model happily calls tools with malformed arguments.

The idea

Engineer the loop, not just the prompt. The pieces that make it production-grade:

  • Tool schemas — each tool is declared to the model as a name + JSON parameter schema; the API constrains generation so arguments parse. The harness validates anyway and feeds errors back as observations — the model reads the error and retries.
  • Loop guards — max iterations, token budgets, timeouts; an unguarded agent loops forever on a stuck task.
  • Context management — old tool outputs get summarized or dropped; long-horizon facts go to external memory (a file, a DB — RAG again) instead of the transcript.
  • Human gates — irreversible actions (send, delete, pay) pause for approval; read-only actions run free. Claude Code’s permission prompts are exactly this line.

Why it matters

  • This is the architecture of Claude Code, Cursor, and every serious agent product — and of the agent you’ll build framework-free for your Phase-2 gate (~150 lines: a while-loop, a tool registry, a transcript).
  • Compounding error is the core open problem — it’s why agent design is mostly about shortening loops, adding checkpoints, and making tools forgiving.
  • Frameworks (LangChain, etc.) wrap this exact loop. Build it bare once and frameworks become optional convenience, not magic.
C3the tool standard

MCP — a standard port for tools

The wall

In the loop above, every tool was hand-wired into one app. N apps × M tools = N×M custom integrations: the GitHub tools you wrote for your agent don’t work in Claude Code, Cursor’s don’t work in yours. Every team rebuilds the same connectors.

The idea

The Model Context Protocol (Anthropic, 2024 — since adopted industry-wide): a USB-C port for AI tools. A server is a small program that exposes tools (functions to call), resources (data to read), and prompts (reusable templates) over a standard JSON-RPC interface. A host (Claude Code, your app) runs a client that connects to any server and asks “what do you offer?” — discovery at runtime, no hardcoding. Write the GitHub server once; every MCP host on earth can use it. N+M instead of N×M.

Why it matters

  • MCP is the 2025–26 answer to “how do agents get capabilities” — OpenAI, Google, and the major IDEs adopted it; connector ecosystems are MCP server directories.
  • For you it’s the highest-leverage build: wrap any API you already know (a MERN backend, ClickUp, your DB) as an MCP server — a weekend project with an instant ecosystem.
  • It cleanly separates concerns: model reasoning (host) vs capability (server) vs permission (host policy) — the same boundary you saw in the agent loop, standardized.
C1the underrated one — measure everything above

Evaluation — how you know any of this works

The wall

Classic ML had accuracy on a held-out test set. With open-ended text there is no single right answer — “is this summary good?” has no equality check. So teams ship on vibes: try five prompts, pick the one that felt best, change a word next week, and never know if anything regressed. You can’t improve what you can’t measure — and every concept on this page (prompts, RAG, agents, sampling settings) changes quality in ways vibes can’t track.

The idea

Build a measurement pipeline — dataset in, score out — choosing the cheapest grader the task allows:

  • Exact / programmatic checks — for extraction, classification, code (run the tests!), math. Cheap, objective, always prefer when possible.
  • LLM-as-judge — a strong model grades outputs against a written rubric. Scales to fuzzy qualities (helpfulness, tone, groundedness), but the judge has biases (prefers long answers, its own style) — spot-check it against human judgment before trusting it.
  • Human eval — the gold standard and the most expensive; used to calibrate the other two and for final calls.

Know the failure modes of public benchmarks (MMLU, HumanEval, …): contamination — the test answers leaked into training data, inflating scores; and Goodhart’s law — once a benchmark becomes the target, models are tuned to it and it stops measuring general ability. Hence private test sets and human preference arenas.

Why it matters

  • Your repo calls this the most underrated skill on the list — correctly. “How would you evaluate it?” is the interview question that separates people who’ve shipped AI from people who’ve demoed it.
  • It composes with everything above: eval your RAG retrieval (is the right chunk in top-k?) separately from generation; eval agent runs by task completion, not step beauty.
  • Minimum viable practice: a JSONL file of real cases + a grading script that runs on every prompt change. That habit alone puts you ahead of most teams.
Part D · Beyond text

Multimodal & diffusion — the other half of generative AI

The journey was text-only. Two concept-level pieces complete the map: how models see (D1), and the different math behind image generation (D2).

D1how models see

Multimodal — images and text in one space

The wall

Everything so far eats tokens. An image is a grid of pixels — no tokens, no vocabulary. And even with a way in, “cat” the word and a photo of a cat live in unrelated representations. How does one model connect them?

The idea

Two steps, both extensions of ideas you know:

  • ViT (Vision Transformer) — chop the image into fixed patches (e.g. 16×16 pixels), flatten each patch into a vector, and treat the patches as a sequence of tokens. Same Transformer, new tokenizer — Lesson 10 didn’t care what the tokens meant.
  • CLIP — train an image encoder and a text encoder together on 400M (image, caption) pairs with a contrastive objective: pull each image’s vector toward its own caption’s vector, push it away from every other caption in the batch. Result: one shared space where meaning is geometry across modalities — Lesson 8’s trick, now spanning pictures.

A modern multimodal assistant is then: vision encoder → project patch vectors into the LLM’s embedding space → the LLM attends over image tokens and text tokens exactly the same way.

Why it matters

  • Explains multimodal pricing and behavior: an image costs tokens because it becomes tokens (often ~700–1600 per image).
  • CLIP-style shared spaces power image search, zero-shot classification, and content moderation — useful even with no generation involved.
  • Pattern to remember: any modality (audio, video, protein sequences) joins the party the same way — find a tokenization, share the space.
D2the other branch

Diffusion — generating by removing noise

The wall

Next-token prediction generates left-to-right, one discrete token at a time. An image isn’t a sequence — it’s a million continuous pixel values that must be globally coherent at once. Autoregression fits it awkwardly; generating pixel #1, then #2… mostly doesn’t produce good pictures. A different generative recipe is needed.

The idea

Learn to destroy, then run it backwards. Training: take a real image, add a little Gaussian noise, again and again until it’s pure static — then train a network (usually a U-Net or Transformer) to predict, at every noise level, what noise was added. That’s a supervised task with a known answer — the same guess→check→adjust loop as ever. Generation: start from pure random noise and apply the network repeatedly — each of ~20–50 steps removes a bit of predicted noise, and an image condenses out. Conditioning steers it: a text embedding (via CLIP-style encoders, D1) is fed into every denoising step so the emerging image is pulled toward the caption — that’s how “a cat astronaut, oil painting” works. Latent diffusion (Stable Diffusion) runs the whole process in a small compressed representation of the image instead of raw pixels, making it cheap enough for consumer GPUs.

Why it matters

  • This is Stable Diffusion, Midjourney, DALL·E, and (extended to video) Sora — the second giant branch of generative AI, with genuinely different math from next-token prediction.
  • The step count explains image-generation latency and the quality/speed knob — fewer denoising steps = faster and rougher.
  • Completes your map: autoregression for sequences of discrete tokens, diffusion for continuous, globally-coherent signals. New generative papers are almost always one of the two (or a hybrid).
